# baltimore

Public repo: embeddable HUD System Performance Measure KPIs for the Baltimore City CoC (MD-501), built with Observable Framework (`src/`, config in `observablehq.config.js`) and deployed to GitHub Pages (https://hmisguru.github.io/baltimore/) by `.github/workflows/deploy.yml`. Companion to the private `hmisguru/baltimore-dac` repo (DAC dashboards + ClientTrack syncs), which is where the data and query logic come from.

**This repo is public.** Never commit credentials, row-level data, internal service IDs/URLs, or anything from `hmisguru/baltimore-dac`'s CLAUDE.md beyond what's needed here. Only CoC-wide aggregates are published. No small-count suppression is applied, per explicit choice: every KPI is a system-wide total or rate.

**Every dashboard ships with both a light and dark theme, from the start** -- per explicit, standing instruction, not a one-off. Use the `dashboard-dark-theme` project skill (`.claude/skills/dashboard-dark-theme/SKILL.md`) for new dashboards and for retrofitting one that doesn't have it yet; it documents the toggle/token pattern, the chart-color technique, and two real gotchas hit building it. Inventory, Bridge and Coordinated Entry all have it.

## Data flow

- `sql/*.sql` are **generated copies** of specific widgets in `balspm.yml` (System Performance Dashboard, `staging` branch of `hmisguru/baltimore-dac`), rendered with no Project filter and with `{{ filters.report_start }}` turned into the BigQuery parameter `@report_start`. Regenerate with `scripts/extract_sql.py <path to balspm.yml>` whenever the dashboard's measure logic changes; never hand-edit, or the published numbers will drift from the dashboard.
- `src/data/spm.json.py` is the only data loader. It reads `MAX(ExportEndDate)` from `balhmiscsv.Export`, reports the most recent **complete** federal fiscal year ending on or before it (FY = Oct 1 – Sep 30), and compares against the prior FY. Measures 1 and 2 are single-period queries, so they run once per FY; 3.2, 5.1, 7a.1 and 7b.1 already return Current/Previous FY columns. Measures 2, 7a.1 and 7b.1 show only a raw count of people, with the change vs. the prior FY as more/fewer people (per explicit request: an earlier version with a secondary percentage line was judged too cluttered). 7a.1's count is the measure's universe (persons exiting Street Outreach) and has `better: null` since neither direction is inherently good; tiles render such changes with a neutral arrow and no Improved/Worsened label. Measure 3.2 (people sheltered) is also `better: null`, per explicit request. It picks one row per measure by exact label and `sys.exit`s if a label is missing, so a changed dashboard query fails the build instead of publishing nulls.
- KPI ids are hardcoded in both the loader (`"id"` fields) and `observablehq.config.js` (`kpiIds`, used for the `/embed/<id>` dynamic paths). Keep the two lists in sync.
- Auth: Application Default Credentials. In CI, the `GCP_SERVICE_ACCOUNT_JSON` repository secret is written to a temp file and pointed to by `GOOGLE_APPLICATION_CREDENTIALS`.

## Exits to permanent housing tile (Measures 7a.1 + 7b.1)

- Per explicit request, the `exits-to-permanent-housing` tile counts people who exited Street Outreach (7a.1) OR ES/SH/TH/RRH/other PH without move-in (7b.1) to a permanent destination (400-499), each person counted once (per explicit choice, over simply adding the two counts; the overlap was 4 people in FY2026 and 11 in FY2025). As of the FY2026 build: 960 (FY2025: 1,091) for all projects, 535 (752) for MOHS-funded.
- `sql/m7_exits_to_ph.sql` is generated by `extract_sql.py` (`COMBINED_PH_EXITS`) from the extracted 7a.1 and 7b.1 queries: both queries' CTEs are kept verbatim through their per-person `classified` CTE (7b.1's renamed with a `b_` prefix), and only the final `COUNT(DISTINCT ...)` over their union is new, so each measure's logic still matches the dashboard. The standalone 7b.1 query no longer runs in the loader; `sql/m7b1_placement.sql` stays as the generator's input.
- The tile is labeled "Measures 7a.1 + 7b.1". The `street-outreach-exits` tile (7a.1 universe) is unchanged.

## MOHS-funded scope

- Per explicit request, embedding sites can limit every KPI to "MOHS-funded" projects: those with a `Funder` record whose `GrantID` is `UNCGF` or `UNBFO` (constant `MOHS_GRANT_IDS` in the loader) active at any point in the two fiscal years compared (previous FY start through current FY end). As of the FY2026 build that's 16 projects: 8 emergency shelters (UNCGF) and 8 Street Outreach projects (UNBFO). The build fails if the grant IDs match no projects, rather than publishing all-zero figures.
- Embedding code opts in with `{mohsFunded: true}` (`KPI`, `KPIGrid`, `data`) or `?mohs=1` on iframe URLs. Grids can also show a visible "MOHS-funded projects only" switch (`KPIGrid(ids, {toggle: true})`, `?toggle=1` on `embed/all`) that swaps between the two scopes client-side, with no extra queries since both are in `spm.json`. It's opt-in per embedding site (off by default, so existing embeds don't change) and grid-only; this site's home page shows it. It's a `<button role="switch" aria-checked>`, the grid footer is `aria-live="polite"` so the scope change is announced, and the knob and track colors clear 3:1 in both themes. `renderKpiGrid` takes the full document and applies `scopeData()` itself; `renderKpi` still takes scoped data. The loader computes every KPI for both scopes, `kpis` (all) and `filters["mohs-funded"].kpis`; `scopeData()` in `kpi.js` picks one and adds "MOHS-funded projects only" to the footer.
- The scope reuses the dashboard's own Project filter placement in each query, parameterized as `(@all_projects OR p.ProjectID IN UNNEST(@project_ids))` by `extract_sql.py`. One deliberate deviation (`UNFILTERED_CTES`): Measure 5.1's `scan_projects` stays CoC-wide, so "first-time" means no prior activity anywhere in the CoC. The dashboard narrows that scan to the filtered projects too, which counted 151 MOHS-shelter entrants with prior non-MOHS activity as first-time in FY2026 (1,605 vs. 1,454). Measure 2 needs no deviation: the dashboard already filters only its universe (PH exits) and searches for returns CoC-wide, per the HUD SPM programming specs. Rule, per explicit instruction: for 5.1 and 2 the filter selects only the initial client universe, which is then compared against the entire CoC. Measures 1a, 7a.1 and 7b.1 deliberately keep the dashboard's logic exactly (their PH/TH negation and "still active" checks stay within the filtered projects); do not change them to CoC-wide.

## Coordinated Entry Line prototype (`/coordinated-entry/`)

- A static Observable rendering of the DAC "Coordinated Entry Line Dashboard", same purpose as the Bridge prototype below (comparing Observable with DAC for a production dashboard), but reading `clienttrack.Call`/`clienttrack.CodeLink` instead of `balhmiscsv`/`baldashboard`. `coordinated-entry/balcoordinatedentry.yml` is a verbatim copy of `balcoordinatedentry.yml` from `hmisguru/baltimore-dac` (staging); refresh it by copying, keeping its header comment.
- Unlike the Bridge dashboard, this one has **no filters and no tabs** — `src/data/coordinated-entry.json.py` runs each of the 7 widgets' SQL exactly once at build time (no filter-combination matrix needed) and writes a flat list of rows plus results. Widget ids `r<row>-w<widget>` match DAC's.
- `src/components/coordinated-entry.js` renders metric, stacked bar, pie (as sorted horizontal bars, same convention as `bridge.js`), and — new, not needed by Bridge — `pivot_table` (a plain cross-tab: one row per `pivot.rows[0]` value, one column per `pivot.columns[0]` value, cell = summed value field, with a Grand Total row only since only the row field has `showTotals: true`). Only this one pivot shape is supported; a future pivot widget with multiple row/column levels would need the renderer extended.
- **Data access:** `clienttrack.*` are plain BigQuery tables (not Sheets-backed), kept fresh by the ClientTrack CTAPI sync in the private `hmisguru/baltimore-dac` repo (`scripts/sync_call.py`/`sync_codelink.py`, via the `baltimore-clientrack-sync` Render service — renamed from `baltimore-call-sync`; same service, same URL (`baltimore-call-sync.onrender.com`), name label only — independent of this site's own build schedule) — so this loader only needs the plain `bigquery` OAuth scope, no Drive scope, no `source_modified` footer logic. **The site's existing `balkpis-public@baldash-508920.iam.gserviceaccount.com` service account needs read access to the `clienttrack` dataset granted before this page's build will succeed** (mirroring how the Bridge dashboard's Sheet was separately shared to it) — not yet confirmed granted as of this page's addition; if the build fails on `coordinated-entry.json.py` with a BigQuery permission error, this is why.
- No About panel, no filter/tab inputs, no embeddable `/embed/coordinated-entry` variant yet — the dashboard itself has none of the former two, and the latter wasn't requested (Bridge's embed page was built later, on request, after its main page; follow the same pattern here if asked).
- **Dark/light theme**, via the `dashboard-dark-theme` skill: the same button toggle as Inventory/Bridge (`renderThemeToggle()`, `ce-theme` localStorage key), `SERIES` as `var(--series-1)`..`var(--series-8)` for the bar/pie charts. No embed page yet, so no `?theme=` param to wire up (see Bridge's embed page if one is ever added here). Simplest of the three retrofits -- no dual-tone tiles, no conditional-format gradient, no muted-token-as-background usage to fix.
- **Collapsible descriptions**, via the `dashboard-collapsible-description` skill: the bar chart, both pies, and the pivot table (everything except the 3 metric tiles, which have no description in this dashboard's YAML at all) collapse their explanatory paragraph below the widget behind a native `<details>/<summary>` ("About this data"), same predicate shape (`widget.type !== "metric"`) and `.ce-card-details` CSS as Inventory's own. The pivot table's description cross-references the two pie charts by name ("the Caller Household Type and Caller Gender pies above"); since neither pie was renamed, no `displayText()`-style cross-reference fixup was needed here.

## Bridge to Housing prototype (`/bridge/`)

- A static Observable rendering of the DAC "Bridge to Housing Dashboard", built to compare Observable with DAC for production dashboards. `bridge/balbridge.yml` is a verbatim copy of `balbridge.yml` from `hmisguru/baltimore-dac` (staging); refresh it by copying, keeping its header comment.
- `src/data/bridge.json.py` runs every widget's own SQL for all 12 filter combinations (4 household types x 3 project types), deduplicated by rendered SQL (190 distinct queries for 372 widget results), and writes the layout plus results (~66 KB, ~11 KB gzipped). Widget ids `r<row>-w<widget>` match DAC's. Tabs are grouped by name in order of first appearance, as DAC does. No SQL is included in the page JSON.
- `src/components/bridge.js` renders each widget from its YAML display config: metric, text (Markdown), line, stacked bar, tables (plain HTML, with DAC's conditional-format pills), pie as sorted horizontal bars, treemap as stacked bars per household type. Series use the validated categorical palette; chrome uses the baltimorecity.gov purple/gold.
- **Data access:** `baldashboard.performance_metrics` is a view over a Google Sheets external table ("BAL Performance Dashboard", owned by daniel@hmisguru.com), so the loader requests the Drive read-only scope. The site build's service account, `balkpis-public@baldash-508920.iam.gserviceaccount.com`, has Viewer access to the Sheet (granted 2026-09-30 and confirmed by running the loader in GitHub Actions: 190 queries in ~60s, none empty). If that sharing is ever removed, the whole site build fails, including the KPIs.
- **About panel at the top**, per explicit request (it used to be a collapsed "About this dashboard" section at the bottom): the YAML's untabbed text notes render open, between the title and the filters, via `renderAbout()` in `bridge.js`. Each note's opening text spans the panel (it carries the DV-shelter exclusion caveat) and its `### ` sections (Interim Housing, Household Types) sit side by side, stacking on narrow screens.
- **Footer:** "Source data last updated <date> · Dashboard refreshed <date, time>", in America/New_York time. The loader reads the Sheet's Drive `modifiedTime` (Sheet id parsed from `baldashboard.sheet`'s external source URI); a failure there only prints a warning and drops the "Source data" part, it never fails the build. That lookup calls the Drive API directly, so the **Google Drive API must be enabled in project `baldash-508920`** (enabled 2026-09-30; BigQuery reads the Sheet without it, but the first deploy got a 403 from Drive until it was turned on). If the footer ever loses its "Source data last updated" date, check the build log for `warning: couldn't read the source Sheet's modified time`.
- **No visible Observable branding**, per explicit request: the site footer is set explicitly (unset, Framework adds "Built with Observable"), no page text names it, and `scripts/strip_generator.js` (run by `npm run build`) removes Framework's `<meta name="generator">` tag from the built pages. Internal element ids and asset paths (`observablehq-*`, `_observablehq/`) stay; they aren't visible.
- **Published by explicit request** at `hmisguru.github.io/baltimore/bridge/` (public, but not linked from the site's home page). The DAC dashboard itself is still staging-only.

- **Embeddable version** at `/embed/bridge` (`src/embed/bridge.md`), built on request: no page header/footer/eyebrow/title, but keeps the About panel, filters, tabs and dated footnote. Both pages share `src/components/bridge.css` (linked with `<link rel="stylesheet">`) and `bridge.js`'s `bridgeInputs()`/`renderFootnote()`; keep page-specific CSS out of the shared file. `?tab=`, `?project=`, `?household=` set the starting state, matched by slug (case/punctuation-insensitive), falling back to defaults.
- **Dark/light theme**, retrofitted via the `dashboard-dark-theme` skill: `/bridge/` gets the same button toggle as Inventory (`renderThemeToggle()`, `bridge-theme` localStorage key); `/embed/bridge` has no visible toggle and instead reads `?theme=dark` off the URL, setting `document.documentElement.dataset.theme` directly rather than through the shared `applyTheme()` (which also persists to `localStorage` -- same-origin-shared with `/bridge/` even when framed elsewhere, so an embed's theme choice must not leak into the main page's own remembered preference). `SERIES` (the categorical chart palette `renderLine`/`renderBar`/`renderPie`/`renderTreemap` all use) is now `var(--series-1)`..`var(--series-8)` rather than raw hex -- modern browsers resolve custom properties in Plot's SVG output same as any other CSS color, confirmed live (toggling recolors every chart, Plot's own legend swatches included, with no re-render) -- light steps on `:root`, the dataviz skill's dark categorical steps under `html[data-theme="dark"]`. `ENGAGEMENT_STATES`' 4 tiles each got an `accentDark`/`bgDark`/`borderDark` trio (Returned's, amber, computed fresh via the accent-blended-16%/37.5%-over-`#2f1c3d` recipe the skill documents, since Inventory's own tiles never needed a 4th hue). `STATUS_COLORS` gained a `neutral: "#52525b"` fixed gray for the "about the same as average" trend pill, replacing a `background:var(--bridge-muted)` that broke in dark mode (that token flips to a *light* lavender there, so its forced-white text became unreadable).
- **Auto-height:** the embed page posts `{type: "baltimore:bridge-height", height}` to `window.parent` from a `ResizeObserver` on `#observablehq-main` (measured by its bounding box, not `scrollHeight`, so it can shrink). The host includes `/bridge-embed.js` (`src/bridge-embed.js`, unhashed via `dynamicPaths`), which accepts only messages from its own origin (`import.meta.url`), sanity-checks the height, sets the matching iframe's height, and replies `baltimore:bridge-autosize`; only then does the embed hide its own scrollbar, so an iframe without the host script still scrolls. In Framework cells write `window.parent`, never bare `parent`: the runtime resolves bare globals as cell inputs and probes the value for `.next`, which throws on a cross-origin window.

## Housing Inventory prototype (`/inventory/`)

- A static Observable rendering of the DAC "Housing Inventory Dashboard", same purpose as the Bridge/Coordinated Entry prototypes above (comparing Observable with DAC for a production dashboard). `inventory/balinventory.yml` is a verbatim copy of `balinventory.yml` from `hmisguru/baltimore-dac` (staging, where it has no header comment to preserve); refresh it by copying.
- `src/data/inventory.json.py` runs every widget's own SQL for all 12 filter combinations (4 household types x 3 HMIS-participation values), same precompute-every-combo-at-build-time approach as `bridge.json.py`. Unlike `balbridge.yml`'s `{{ filters.x }}` usage inside Jinja conditionals, `balinventory.yml`'s filters are interpolated as bare literal strings directly into each query's `WHERE` clause (e.g. `'{{ filters.household_type }}' = 'All'`), so nearly every widget's rendered SQL is genuinely distinct per combination -- 9 widgets x 12 combos = 108 widget results, only 97 distinct queries (just the filter-blind "Methodology" tile dedupes, 12 -> 1). Widget ids `r<row>-w<widget>` match DAC's; rows have no `tab` key (single-page dashboard), so the layout is a flat list like `coordinated-entry.json.py`'s, not tabs like `bridge.json.py`'s.
- **Data access:** reads `balhmiscsv` plus `clienttrack.HMISPITCount` (the non-HMIS-participating utilization fallback) -- the same `clienttrack` dataset grant the Coordinated Entry loader needs, already confirmed working (every build since Coordinated Entry shipped has succeeded). No Google Sheets/Drive involvement, so this loader only needs the plain `bigquery` OAuth scope.
- **Pivot shape:** both `pivot_table` widgets here (`Current Inventory by Project Type`, `Current Inventory by Project`) nest two ROW levels (project type, then household type or project name) with no column dimension at all and three side-by-side value columns (Beds, Units, Average Utilization) -- a different shape from `coordinated-entry.js`'s existing `renderPivotTable()` (single row field x single column field, one summed value), so `src/components/inventory.js` has its own `renderNestedPivot()`: the outer row level is shown once per group via `rowspan`, each inner row lists its own value cells, and the queries already pre-aggregate to the exact (outer, inner) grain -- no client-side re-aggregation, pure layout. Project type rows sort in this dashboard's own tile order (Emergency Shelter, Safe Haven, Transitional Housing, Rapid Re-Housing, Permanent Supportive Housing, Other Permanent Housing), not SQL's arbitrary `GROUP BY` order; project names sort alphabetically within each group.
- **Gradient conditional format:** Average Utilization's DAC format rule (`backgroundColor: [red, amber, green], range: [0, 0.5, 1], unit: absolute`) is a gradient layer, not a discrete `if:`-keyed rule like `bridge.js`'s existing pill colors -- `gradientFor()` linearly interpolates between stops in RGB space. Per explicit request, light and dark mode use different stops rather than one fixed set: `GRADIENT_COLORS_LIGHT` keeps the original pastel tints (`#FECACA`/`#FDE68A`/`#BBF7D0`, dark cell text) that suit the dashboard's light surface; `GRADIENT_COLORS_DARK` uses deeper, more saturated tones (`#B91C1C`/`#92400E`/`#166534`, white cell text) that suit Baltimore City's purple/gold branding against the dark surface, where pastel looked washed out. Both backgrounds are computed in JS and passed through as the `--grad-bg`/`--grad-bg-dark` custom properties on each cell (same convention as `--tile-accent`/`--tile-accent-dark` above); `.inv-grad-cell`/`html[data-theme="dark"] .inv-grad-cell` in `inventory.css` pick the active one and matching text color, so no re-render is needed on theme toggle. Utilization over 100% (real, confirmed live -- e.g. one Rapid Re-Housing project at 166%) renders as-is past the green end, not capped or clamped to some artificial max.
- **Display-only tweaks, per explicit request, none of which touch `balinventory.yml`:** the first pivot table renders as "Current Inventory by Household Type" (its own `name` field stays DAC's verbatim "Current Inventory by Project Type"; `TITLE_OVERRIDES` in `inventory.js` swaps it at render time, including inside the second table's own description text, which cross-references the first by name). Both pivot tables' explanatory paragraph moves below the table and collapses behind a native `<details>/<summary>` ("About this data" -- the `dashboard-collapsible-description` skill's generic default, not "About this table", since that pattern isn't table-specific), so the table itself is the first thing in view.
- **Population badges:** "Current Inventory by Project" marks each project with a small fixed-color pill next to its name for each dedicated population it actively serves -- DV (violet, HUD's Project.csv `TargetPopulation = 1`), Vets (blue), Youth (green), stacked in that order when a project carries more than one (`POPULATION_BADGES`/`.inv-pop-badge` in `inventory.js`/`.css`). Per explicit instruction DV is safe to publish on this public site -- note that's a deliberate departure from the Bridge dashboard's own DV handling (which excludes DV shelters entirely, since they're non-HMIS-participating; see the Bridge section below). Project names come from `inventory.json.py`'s `dv_project_names()` (`SELECT DISTINCT ProjectName FROM balhmiscsv.Project WHERE TargetPopulation = 1`) and `active_population_project_names()` (HUD's Inventory.csv `VetBedInventory`/`YouthBedInventory > 0`, restricted to inventory rows ACTIVE as of the HMIS export's own `MAX(ExportEndDate)` -- the same active-inventory window balinventory.yml's own widgets use throughout) -- one-off queries outside the YAML's own widgets, matched onto pivot rows by name since that table's own query only groups down to `(project_type_label, project_name)` with no `ProjectID` carried through.
- **No embeddable variant, not linked from the site's home page** -- same as Coordinated Entry's own initial state; add one if asked, following Bridge's `/embed/bridge` pattern.

## City Performance Measures prototype (`/city-performance/`)

- A ground-up HMIS CSV replacement for `FY27_Measures_and_Notes.xlsx` (a workbook the City maintains, not a DAC dashboard like every other prototype above) -- that workbook's 19 measures, across 4 service categories (Homeless Prevention, Outreach to the Homeless, Permanent Housing, Temporary Housing), currently get pulled by hand each quarter from a mix of manual "HMIS Active Client List" report exports, HUD SPM/APR report pulls, and annual PIT/HIC submissions. The workbook itself is never committed here -- it's a City document with a named point of contact, not public CoC data -- only the measure definitions and historical figures it was used to validate against.
- **Not linked from the site's home page; built and reviewed one service category at a time, like every other dashboard here.** Built so far: "Outreach to the Homeless" (Measure IDs 8941, 8942, 8943 -- street outreach enrollments, their overlap with Coordinated Access, and successful exits; `sql/city_outreach.sql`), "Homeless Prevention" (8931, 8932 -- active Prevention enrollments and the household-level first-time-homeless rate; `sql/city_prevention.sql`), most of "Permanent Housing" (8961, 8964, 8965 -- household PH retention, PH bed count, and household returns after a PH exit; `sql/city_permanent.sql`), and most of "Temporary Housing" (8951, 8952, 8957 -- exits to PH, average length of time homeless, and ES bed count; `sql/city_temporary.sql`). **8962/8963 (Permanent Housing) and 8953/8954 (Temporary Housing) -- all four of the workbook's income-growth measures, HUD SPM 4/APR Q19 -- aren't built yet.** Income growth is a substantial new methodology -- annual-assessment-vs-entry income comparison for adult leavers+stayers -- not reused from anywhere else in this repo (unlike every other measure here, which adapts existing `sql/m*.sql` logic or `inventory.json.py`'s bed-count pattern), so it's deliberately scoped out to its own follow-up covering all four at once rather than rushed into either housing-type slice. Cards render grouped under a heading per service category, in the order each category's measures first appear in `doc.measures` (`renderMeasures()` in `city-performance.js`); each measure object carries its own `"service"` field, and the JSON's top-level `"services"` list is derived from them (`list(dict.fromkeys(...))`, so insertion order is preserved) rather than hardcoded.
- **PIT-sourced measures (8955, 8956) are out of scope entirely, not just deferred** -- a Point-in-Time count is a single-night manual count, not continuous HMIS enrollment data, so it structurally can't be computed this way. Same reasoning the Westchester repo's own `spm.json.py` already documents for omitting PIT there.
- **Uses the City's own fiscal year (July 1 - June 30, confirmed against the workbook's "CFY" quarter columns), not the federal fiscal year (Oct 1 - Sep 30) every other dashboard in this repo uses.** `src/data/city-performance.json.py`'s `city_quarters()`/`cfy_label()` compute city fiscal quarters and label them by the calendar year they end in (e.g. Oct-Dec 2024 is "CFY25 Q2"), independent of `spm.json.py`'s own `fiscal_year()`.
- **`sql/city_outreach.sql` is hand-written**, not extracted from a DAC YAML -- there's no `balspm.yml` widget to copy from, since this dashboard doesn't mirror an existing DAC dashboard at all. Takes `@report_start`/`@report_end` directly (an explicit end date, unlike every other `sql/*.sql` file's implicit "+1 year" window) since city fiscal quarters are 3 months, not a year.
  - **Street Outreach is scoped to three specific projects, per explicit request** -- `so_projects` matches `ProjectID IN (19876, 19922, 19586)` (DPOB - Downtown Partnership Street Outreach, MOHS Homeless Outreach, PEP-Mobile Outreach & Treatment Project), not every `ProjectType = 4` project CoC-wide like `sql/m3_sheltered.sql`'s own `qualifying_projects` stays. Matched by `ProjectID`, not `ProjectName`, so a later rename doesn't silently drop one. Deliberately excludes several similarly-named SO projects also live in `balhmiscsv.Project` (MOHS District 10 Street Outreach, MOHS Encampment Outreach, PEP-BCORE Outreach & Treatment Program, PEP-SUD Outreach & Treatment Program) and Franciscan Center Street Outreach, which the workbook's own notes for measure 8942 once listed alongside these three -- this scoping request named only three, so Franciscan Center stays out. This scoping applies to all three measures (8941/8942/8943), since 8942 and 8943 are both computed from the same Street-Outreach-enrolled cohort as 8941, not a separately-scoped population; only 8942's Coordinated Entry side (`ce_projects`) stays CoC-wide.
  - Measure 8941 (street outreach enrollments) and 8942 (% also enrolled in Coordinated Access, ProjectType 14) both use this repo's own Active-Clients convention (`EntryDate <= period_end AND (no exit, or exit after period_start)`, same as `sql/m3_sheltered.sql`), not the legacy report's method -- expect these figures to diverge from the workbook's own historical numbers for that reason, not as a bug.
  - Measure 8943 (% of street outreach exits to shelter/Safe Haven/transitional housing/permanent housing) buckets `Exit.Destination` into success (101, 118, or 300-499) vs. not. **Destination 116 ("place not meant for habitation") is deliberately excluded even though it falls inside the 100-199 range** -- it means the person is still unsheltered, not a successful exit. An earlier draft that bucketed the whole 100-199 range as "shelter" came out ~3x too high against the workbook's own historical rate; catching 116 specifically was the fix. Institutional (200-299) and other/unknown (8, 9, 17, 24, 30, 37, 99) destinations never count as success either.
  - FY25/FY26/FY27 targets (`TARGETS` in the loader) are copied directly from the workbook's own Results sheet -- not derived from HMIS data at all, and not expected to change unless the workbook's own targets do.
- **`sql/city_prevention.sql` is likewise hand-written**, for the "Homeless Prevention" service category (8931, 8932). `src/data/city-performance.json.py`'s `run_period()` merges results from every file in the `SQL_FILES` dict (one query per file per period, same `@report_start`/`@report_end` params) rather than hardcoding a single query -- adding a category means adding its SQL file to that dict, not restructuring the runner.
  - Measure 8931 (active Homeless Prevention enrollments, `ProjectType = 12`) uses the same Active-Clients convention as 8941/m3_sheltered.sql; same expected divergence from the workbook's legacy figures (e.g. 386 vs. the workbook's 294 for CFY25 Q1).
  - Measure 8932 (% of households entering ES/SH/TH with no prior ES/SH/TH/PH enrollment in the past 2 years) is the household-level variant (HUD SPM 5.2) of `sql/m5_first_time.sql`'s existing person-level 5.1 logic -- `entry_projects`/`scan_projects` and the lookback rule (`GREATEST(report_start - 7yr, client_start - 730 days)`) are copied verbatim from there; only the population is restricted to Heads of Household (`RelationshipToHoH = 1`) and `HouseholdID` is carried through instead of counting every household member. `better: "lower"` (the workbook's own "Decrease" desired-outcome direction), unlike 8941/8942/8943's `"higher"`.
- **`sql/city_permanent.sql`** covers three of Permanent Housing's five measures (8962/8963 income growth deferred, see above). "PH" throughout means PSH + Other Permanent Housing (`ProjectType IN (3, 9)`) only, never RRH (`10`) -- same convention 8964's own workbook description ("PSH and OPH beds") sets for the whole category.
  - Measure 8961 (% of households retaining permanent housing) was reverse-engineered against the workbook's own historical rate rather than derived from a HUD spec document directly: a household (by Head of Household, moved in, active or exited in the period) counts as retained if it's still active OR its exit destination isn't a literal "still homeless" code (100-199); households whose exit destination is a non-informative code (client doesn't know/refused, no exit interview, data not collected, deceased, or invalid/deleted -- `8, 9, 17, 24, 30, 99, 206, 215, 225`) are excluded from the universe entirely, the same exclusion pattern as `sql/m7b1_placement.sql`'s own narrower 4-code list. This combination was found by testing against the workbook's own CFY25/CFY26 Q1 figures and landed within half a point (98.6% vs. 98.51%; 99.5% vs. 99.14%) -- much tighter than this dashboard's other measures, since it's reconstructing HUD's own exit-destination classification rather than reproducing a differently-computed legacy report.
  - Measure 8964 (PH beds) sums `balhmiscsv.Inventory.BedInventory` for PSH/OPH projects active as of `report_end`, same `InventoryStartDate <= as_of AND (InventoryEndDate IS NULL OR InventoryEndDate >= as_of)` convention as `inventory.json.py`'s own active-inventory window -- a point-in-time snapshot, not a true annual HIC submission, so expect it to diverge from the workbook's "Previous FY HIC" figures (e.g. 4,951 here vs. 5,362 in the workbook for CFY25 Q1) the same way every other measure in this dashboard does.
  - Measure 8965 (% of households who returned to a homeless service project within 2 years of a PH exit) adapts `sql/m2_returns.sql`'s existing "TOTAL Returns to Homelessness" row logic (the candidates/matches CTEs, the 14-day PH re-entry grace period, the NOT EXISTS overlap check) with two changes: `@report_start`/`@report_end` taken directly instead of implying a 1-year window, and the exiting side restricted to Heads of Household only, same HoH-as-household-proxy approximation as 8932 -- the return side still scans CoC-wide by `PersonalID`, unchanged. Matches the workbook closely (18.2% vs. 18.6% for CFY25 Q1; 14.7% vs. 14.6% for CFY26 Q1).
- **`sql/city_temporary.sql`** covers three of Temporary Housing's five non-PIT measures (8953/8954 income growth deferred, see above; 8955/8956 are PIT, out of scope entirely).
  - Measure 8951 (% of persons exiting ES/SH/TH/RRH/PH-without-move-in to a permanent destination) is a near-verbatim reuse of `sql/m7b1_placement.sql`'s own full classification pipeline (own_movein/hoh_movein/effective_movein, the still-active leavers filter, the 4-code exclude list `206, 215, 225, 24`) with `@report_start`/`@report_end` taken directly instead of implying a 1-year window -- this measure's own workbook methodology cites HUD SPM 7b.1 by name, so it's the most direct reuse in this dashboard. Matches the workbook's rate closely (33.9% vs. 34.07% for CFY25 Q1).
  - Measure 8952 (average length of time, in days, persons are continuously enrolled in ES/SH/TH -- HUD SPM 1a.2) is a trimmed copy of `sql/m1_length_of_time.sql`'s own row 2 ("Persons in ES-EE, ES-NbN, SH, and TH") from its `_base` (1a, no self-reported start date) computation only -- the self-report CTEs and the TH-negation/PH-own-nights logic that only rows 1/3/4 need are dropped entirely, since row 2 negates solely by PH move-in. `@report_start`/`@report_end` taken directly; correctness isn't affected by period length since every CTE is already bound through `bounds.report_start`/`report_end`. Same-ballpark match to the workbook (230.4 vs. 217.1 days for CFY25 Q1; 228.4 vs. 216.9 for CFY26 Q1), same divergence-is-expected posture as this dashboard's other measures -- not the near-exact match 8961/8965 get, since this one (like 8941/8931) is Active-Clients-style continuous-enrollment logic rather than a straight exit-destination reclassification.
  - Measure 8957 (ES beds) sums `balhmiscsv.Inventory.BedInventory` for `ProjectType IN (0, 1)` (ES-EE + ES-NbN only, not Safe Haven, matching the workbook's literal "emergency shelter" naming) active as of `report_end`, same point-in-time-snapshot convention as 8964's own PSH/OPH bed count. `better: null` (the workbook's own "N/A" desired-outcome direction, same neutral treatment `spm.json.py`'s 7a.1/3.2 KPIs already use) -- `renderAnnualTable()` in `city-performance.js` was fixed to never highlight a `null`-`better` measure's actual-vs-target cell as "met" (it previously fell through to the "lower is better" branch, which would have wrongly colored es-beds' cells based on an outcome direction the measure doesn't have).
- `src/components/city-performance.js`/`.css` render it: one card per measure (`cpm-` class prefix), each with a stat for the "viewing" quarter vs. the quarter before it (same Improved/Worsened convention as `kpi.js`'s `statusOf()`, just quarterly instead of annual), a quarterly trend line (Observable Plot) with a dashed rule at the latest complete fiscal year's target, an actual-vs-target table per complete CFY, and the measure's own methodology collapsed below via `<details>` (`dashboard-collapsible-description` pattern). Dark theme from the start (`cpm-theme` localStorage key, same toggle/token pattern as every other dashboard here) -- per the standing CLAUDE.md rule, not retrofitted.
- **Quarter-picker slider**, per explicit request: a single `<input type="range">` above the card grid, covering the current quarter plus the 4 before it (`recentQuarters(doc, 5)`), default rightmost (current). Moving it re-renders every card's stat and trend-chart highlight (a filled dot + dashed vertical rule at the selected quarter) via `renderMeasures(doc, selectedLabel)` -- cheap since every quarter is already in `doc`, no refetch. The delta is still computed against the full quarter series (so picking the window's oldest quarter, e.g. CFY26 Q1, correctly compares against CFY25 Q4, one quarter before the slider's own 5-quarter range). The per-CFY actual-vs-target table is intentionally unaffected by the slider -- it's a separate full-year view, not a quarterly one.

## Embedding surfaces (keep all three working)

1. **Iframes**: `src/embed/[kpi].md` (one parameterized page per KPI) and `src/embed/all.md` (grid). Chrome-free (no header/footer/sidebar), `?theme=light|dark` override.
2. **Exported JS module**: `src/kpis.js` → published unhashed at `/kpis.js` via `dynamicPaths`. Exports `KPI(id, options)`, `KPIGrid(ids, options)`, `data()`. Its `FileAttachment` resolves relative to `import.meta.url`, so cross-origin imports work (GitHub Pages sends `Access-Control-Allow-Origin: *`).
3. **Raw JSON**: `/data/spm.json`, also via `dynamicPaths`.

`src/components/kpi.js` is the one tile renderer all three share: plain DOM, no dependencies, self-injected CSS scoped to `.bkpi`, restylable via `--bkpi-*` custom properties. Styled to match baltimorecity.gov (purple/gold palette, Proxima Nova via the host page's Typekit, Nunito Sans fallback), light by default since that site has no dark mode (`theme: "dark"` or `"auto"` opt in). In `renderKpiGrid`, tiles use CSS subgrid (`grid-row: span <tile part count>` + `grid-template-rows: subgrid`) so each part (label, title, value, change, description) aligns across tiles in the same row even when titles wrap differently; browsers without subgrid fall back to normal stacking. Delta color is never the only signal: every tile shows an arrow plus an "Improved"/"Worsened"/"No change" label, based on each KPI's `better` direction.

## Scheduling

Monthly on the first Wednesday (13:17 UTC), plus on push to `main` and manual dispatch. Cron ORs day-of-month with day-of-week, so the schedule fires every Wednesday (`17 13 * * 3`) and a `schedule-gate` job skips `build`/`deploy` unless the UTC date is the 1st-7th; pushes and manual runs always build. GitHub disables scheduled workflows in public repos after 60 days of no repo activity; the `keepalive` job re-enables the workflow via the API on each scheduled run to reset that clock.
