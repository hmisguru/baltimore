# baltimore-kpis

Public repo: embeddable HUD System Performance Measure KPIs for the Baltimore City CoC (MD-501), built with Observable Framework (`src/`, config in `observablehq.config.js`) and deployed to GitHub Pages (https://hmisguru.github.io/baltimore-kpis/) by `.github/workflows/deploy.yml`. Companion to the private `hmisguru/baltimore` repo (DAC dashboards + ClientTrack syncs), which is where the data and query logic come from.

**This repo is public.** Never commit credentials, row-level data, internal service IDs/URLs, or anything from `hmisguru/baltimore`'s CLAUDE.md beyond what's needed here. Only CoC-wide aggregates are published. No small-count suppression is applied, per explicit choice: every KPI is a system-wide total or rate.

## Data flow

- `sql/*.sql` are **generated copies** of specific widgets in `balspm.yml` (System Performance Dashboard, `staging` branch of `hmisguru/baltimore`), rendered with no Project filter and with `{{ filters.report_start }}` turned into the BigQuery parameter `@report_start`. Regenerate with `scripts/extract_sql.py <path to balspm.yml>` whenever the dashboard's measure logic changes; never hand-edit, or the published numbers will drift from the dashboard.
- `src/data/spm.json.py` is the only data loader. It reads `MAX(ExportEndDate)` from `balhmiscsv.Export`, reports the most recent **complete** federal fiscal year ending on or before it (FY = Oct 1 – Sep 30), and compares against the prior FY. Measures 1 and 2 are single-period queries, so they run once per FY; 3.2, 5.1, 7a.1 and 7b.1 already return Current/Previous FY columns. Measures 2, 7a.1 and 7b.1 show only a raw count of people, with the change vs. the prior FY as more/fewer people (per explicit request: an earlier version with a secondary percentage line was judged too cluttered). 7a.1's count is the measure's universe (persons exiting Street Outreach) and has `better: null` since neither direction is inherently good; tiles render such changes with a neutral arrow and no Improved/Worsened label. Measure 3.2 (people sheltered) is also `better: null`, per explicit request. It picks one row per measure by exact label and `sys.exit`s if a label is missing, so a changed dashboard query fails the build instead of publishing nulls.
- KPI ids are hardcoded in both the loader (`"id"` fields) and `observablehq.config.js` (`kpiIds`, used for the `/embed/<id>` dynamic paths). Keep the two lists in sync.
- Auth: Application Default Credentials. In CI, the `GCP_SERVICE_ACCOUNT_JSON` repository secret is written to a temp file and pointed to by `GOOGLE_APPLICATION_CREDENTIALS`.

## Exits to permanent housing tile (Measures 7a.1 + 7b.1)

- Per explicit request, the `exits-to-permanent-housing` tile counts people who exited Street Outreach (7a.1) OR ES/SH/TH/RRH/other PH without move-in (7b.1) to a permanent destination (400-499), each person counted once (per explicit choice, over simply adding the two counts; the overlap was 4 people in FY2026 and 11 in FY2025). As of the FY2026 build: 960 (FY2025: 1,091) for all projects, 535 (752) for MOHS-funded.
- `sql/m7_exits_to_ph.sql` is generated by `extract_sql.py` (`COMBINED_PH_EXITS`) from the extracted 7a.1 and 7b.1 queries: both queries' CTEs are kept verbatim through their per-person `classified` CTE (7b.1's renamed with a `b_` prefix), and only the final `COUNT(DISTINCT ...)` over their union is new, so each measure's logic still matches the dashboard. The standalone 7b.1 query no longer runs in the loader; `sql/m7b1_placement.sql` stays as the generator's input.
- The tile is labeled "Measures 7a.1 + 7b.1". The `street-outreach-exits` tile (7a.1 universe) is unchanged.

## MOHS-funded scope

- Per explicit request, embedding sites can limit every KPI to "MOHS-funded" projects: those with a `Funder` record whose `GrantID` is `UNCGF` or `UNBFO` (constant `MOHS_GRANT_IDS` in the loader) active at any point in the two fiscal years compared (previous FY start through current FY end). As of the FY2026 build that's 16 projects: 8 emergency shelters (UNCGF) and 8 Street Outreach projects (UNBFO). The build fails if the grant IDs match no projects, rather than publishing all-zero figures.
- Embedding code opts in with `{mohsFunded: true}` (`KPI`, `KPIGrid`, `data`) or `?mohs=1` on iframe URLs. Grids can also show a visible "MOHS-funded projects only" switch (`KPIGrid(ids, {toggle: true})`, `?toggle=1` on `embed/all`) that swaps between the two scopes client-side, with no extra queries since both are in `spm.json`. It's opt-in per embedding site (off by default, so existing embeds don't change) and grid-only; this site's home page shows it. It's a `<button role="switch" aria-checked>`, the grid footer is `aria-live="polite"` so the scope change is announced, and the knob and track colors clear 3:1 in both themes. `renderKpiGrid` takes the full document and applies `scopeData()` itself; `renderKpi` still takes scoped data. The loader computes every KPI for both scopes, `kpis` (all) and `filters["mohs-funded"].kpis`; `scopeData()` in `kpi.js` picks one and adds "MOHS-funded projects only" to the footer.
- The scope reuses the dashboard's own Project filter placement in each query, parameterized as `(@all_projects OR p.ProjectID IN UNNEST(@project_ids))` by `extract_sql.py`. One deliberate deviation (`UNFILTERED_CTES`): Measure 5.1's `scan_projects` stays CoC-wide, so "first-time" means no prior activity anywhere in the CoC. The dashboard narrows that scan to the filtered projects too, which counted 151 MOHS-shelter entrants with prior non-MOHS activity as first-time in FY2026 (1,605 vs. 1,454). Measure 2 needs no deviation: the dashboard already filters only its universe (PH exits) and searches for returns CoC-wide, per the HUD SPM programming specs. Rule, per explicit instruction: for 5.1 and 2 the filter selects only the initial client universe, which is then compared against the entire CoC. Measures 1a, 7a.1 and 7b.1 deliberately keep the dashboard's logic exactly (their PH/TH negation and "still active" checks stay within the filtered projects); do not change them to CoC-wide.

## Coordinated Entry Line prototype (`/coordinated-entry/`)

- A static Observable rendering of the DAC "Coordinated Entry Line Dashboard", same purpose as the Bridge prototype below (comparing Observable with DAC for a production dashboard), but reading `clienttrack.Call`/`clienttrack.CodeLink` instead of `balhmiscsv`/`baldashboard`. `coordinated-entry/balcoordinatedentry.yml` is a verbatim copy of `balcoordinatedentry.yml` from `hmisguru/baltimore` (staging); refresh it by copying, keeping its header comment.
- Unlike the Bridge dashboard, this one has **no filters and no tabs** — `src/data/coordinated-entry.json.py` runs each of the 7 widgets' SQL exactly once at build time (no filter-combination matrix needed) and writes a flat list of rows plus results. Widget ids `r<row>-w<widget>` match DAC's.
- `src/components/coordinated-entry.js` renders metric, stacked bar, pie (as sorted horizontal bars, same convention as `bridge.js`), and — new, not needed by Bridge — `pivot_table` (a plain cross-tab: one row per `pivot.rows[0]` value, one column per `pivot.columns[0]` value, cell = summed value field, with a Grand Total row only since only the row field has `showTotals: true`). Only this one pivot shape is supported; a future pivot widget with multiple row/column levels would need the renderer extended.
- **Data access:** `clienttrack.*` are plain BigQuery tables (not Sheets-backed), kept fresh by the ClientTrack CTAPI sync in the private `hmisguru/baltimore` repo (`scripts/sync_call.py`/`sync_codelink.py`, via the `baltimore-clientrack-sync` Render service — renamed from `baltimore-call-sync`; same service, same URL (`baltimore-call-sync.onrender.com`), name label only — independent of this site's own build schedule) — so this loader only needs the plain `bigquery` OAuth scope, no Drive scope, no `source_modified` footer logic. **The site's existing `balkpis-public@baldash-508920.iam.gserviceaccount.com` service account needs read access to the `clienttrack` dataset granted before this page's build will succeed** (mirroring how the Bridge dashboard's Sheet was separately shared to it) — not yet confirmed granted as of this page's addition; if the build fails on `coordinated-entry.json.py` with a BigQuery permission error, this is why.
- No About panel, no filter/tab inputs, no embeddable `/embed/coordinated-entry` variant yet — the dashboard itself has none of the former two, and the latter wasn't requested (Bridge's embed page was built later, on request, after its main page; follow the same pattern here if asked).

## Bridge to Housing prototype (`/bridge/`)

- A static Observable rendering of the DAC "Bridge to Housing Dashboard", built to compare Observable with DAC for production dashboards. `bridge/balbridge.yml` is a verbatim copy of `balbridge.yml` from `hmisguru/baltimore` (staging); refresh it by copying, keeping its header comment.
- `src/data/bridge.json.py` runs every widget's own SQL for all 12 filter combinations (4 household types x 3 project types), deduplicated by rendered SQL (190 distinct queries for 372 widget results), and writes the layout plus results (~66 KB, ~11 KB gzipped). Widget ids `r<row>-w<widget>` match DAC's. Tabs are grouped by name in order of first appearance, as DAC does. No SQL is included in the page JSON.
- `src/components/bridge.js` renders each widget from its YAML display config: metric, text (Markdown), line, stacked bar, tables (plain HTML, with DAC's conditional-format pills), pie as sorted horizontal bars, treemap as stacked bars per household type. Series use the validated categorical palette; chrome uses the baltimorecity.gov purple/gold.
- **Data access:** `baldashboard.performance_metrics` is a view over a Google Sheets external table ("BAL Performance Dashboard", owned by daniel@hmisguru.com), so the loader requests the Drive read-only scope. The site build's service account, `balkpis-public@baldash-508920.iam.gserviceaccount.com`, has Viewer access to the Sheet (granted 2026-09-30 and confirmed by running the loader in GitHub Actions: 190 queries in ~60s, none empty). If that sharing is ever removed, the whole site build fails, including the KPIs.
- **About panel at the top**, per explicit request (it used to be a collapsed "About this dashboard" section at the bottom): the YAML's untabbed text notes render open, between the title and the filters, via `renderAbout()` in `bridge.js`. Each note's opening text spans the panel (it carries the DV-shelter exclusion caveat) and its `### ` sections (Interim Housing, Household Types) sit side by side, stacking on narrow screens.
- **Footer:** "Source data last updated <date> · Dashboard refreshed <date, time>", in America/New_York time. The loader reads the Sheet's Drive `modifiedTime` (Sheet id parsed from `baldashboard.sheet`'s external source URI); a failure there only prints a warning and drops the "Source data" part, it never fails the build. That lookup calls the Drive API directly, so the **Google Drive API must be enabled in project `baldash-508920`** (enabled 2026-09-30; BigQuery reads the Sheet without it, but the first deploy got a 403 from Drive until it was turned on). If the footer ever loses its "Source data last updated" date, check the build log for `warning: couldn't read the source Sheet's modified time`.
- **No visible Observable branding**, per explicit request: the site footer is set explicitly (unset, Framework adds "Built with Observable"), no page text names it, and `scripts/strip_generator.js` (run by `npm run build`) removes Framework's `<meta name="generator">` tag from the built pages. Internal element ids and asset paths (`observablehq-*`, `_observablehq/`) stay; they aren't visible.
- **Published by explicit request** at `hmisguru.github.io/baltimore-kpis/bridge/` (public, but not linked from the site's home page). The DAC dashboard itself is still staging-only.

- **Embeddable version** at `/embed/bridge` (`src/embed/bridge.md`), built on request: no page header/footer/eyebrow/title, but keeps the About panel, filters, tabs and dated footnote. Both pages share `src/components/bridge.css` (linked with `<link rel="stylesheet">`) and `bridge.js`'s `bridgeInputs()`/`renderFootnote()`; keep page-specific CSS out of the shared file. `?tab=`, `?project=`, `?household=` set the starting state, matched by slug (case/punctuation-insensitive), falling back to defaults.
- **Auto-height:** the embed page posts `{type: "baltimore-kpis:bridge-height", height}` to `window.parent` from a `ResizeObserver` on `#observablehq-main` (measured by its bounding box, not `scrollHeight`, so it can shrink). The host includes `/bridge-embed.js` (`src/bridge-embed.js`, unhashed via `dynamicPaths`), which accepts only messages from its own origin (`import.meta.url`), sanity-checks the height, sets the matching iframe's height, and replies `baltimore-kpis:bridge-autosize`; only then does the embed hide its own scrollbar, so an iframe without the host script still scrolls. In Framework cells write `window.parent`, never bare `parent`: the runtime resolves bare globals as cell inputs and probes the value for `.next`, which throws on a cross-origin window.

## Embedding surfaces (keep all three working)

1. **Iframes**: `src/embed/[kpi].md` (one parameterized page per KPI) and `src/embed/all.md` (grid). Chrome-free (no header/footer/sidebar), `?theme=light|dark` override.
2. **Exported JS module**: `src/kpis.js` → published unhashed at `/kpis.js` via `dynamicPaths`. Exports `KPI(id, options)`, `KPIGrid(ids, options)`, `data()`. Its `FileAttachment` resolves relative to `import.meta.url`, so cross-origin imports work (GitHub Pages sends `Access-Control-Allow-Origin: *`).
3. **Raw JSON**: `/data/spm.json`, also via `dynamicPaths`.

`src/components/kpi.js` is the one tile renderer all three share: plain DOM, no dependencies, self-injected CSS scoped to `.bkpi`, restylable via `--bkpi-*` custom properties. Styled to match baltimorecity.gov (purple/gold palette, Proxima Nova via the host page's Typekit, Nunito Sans fallback), light by default since that site has no dark mode (`theme: "dark"` or `"auto"` opt in). In `renderKpiGrid`, tiles use CSS subgrid (`grid-row: span <tile part count>` + `grid-template-rows: subgrid`) so each part (label, title, value, change, description) aligns across tiles in the same row even when titles wrap differently; browsers without subgrid fall back to normal stacking. Delta color is never the only signal: every tile shows an arrow plus an "Improved"/"Worsened"/"No change" label, based on each KPI's `better` direction.

## Scheduling

Monthly on the first Wednesday (13:17 UTC), plus on push to `main` and manual dispatch. Cron ORs day-of-month with day-of-week, so the schedule fires every Wednesday (`17 13 * * 3`) and a `schedule-gate` job skips `build`/`deploy` unless the UTC date is the 1st-7th; pushes and manual runs always build. GitHub disables scheduled workflows in public repos after 60 days of no repo activity; the `keepalive` job re-enables the workflow via the API on each scheduled run to reset that clock.
