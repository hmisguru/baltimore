# Dashboard port

Extracted from porting the Bridge to Housing dashboard from this site's `hmisguru/baltimore` + `hmisguru/baltimore-dac` repo pair into a sibling CoC's `hmisguru/westchester` + `hmisguru/westchester-dac` pair — a multi-session effort that went through a full build, then several rounds of the destination's maintainer doing a side-by-side comparison against the *source's actual live page* and calling out specific gaps, until the two were at genuine feature parity. Everything below generalizes past that one port: "source" and "destination" each mean a public Observable repo + its private DAC repo, in either direction.

## The pattern in one paragraph

A dashboard here is four layers: a DAC YAML (`<name>.yml`, lives in the `-dac` repo, the single source of truth for widgets/filters/SQL), a Python loader (`src/data/<name>.json.py`, runs every widget's SQL for every filter combination and writes one JSON document), a JS+CSS renderer (`src/components/<name>.js`/`.css`), and a thin `src/<name>/index.md` page that wires the three together. Porting means standing up all four in the destination's own repo pair, adapted to its own BigQuery project/dataset/table names and its own site's visual identity, while preserving the *logic* — filter shapes, widget SQL, hidden-widget conventions, display overrides — exactly. The work is never "done" after one pass: treat the first build as a draft, then do a real side-by-side comparison against the source's *actual rendered output* (not just its YAML) and keep closing gaps the maintainer calls out, the same iterative loop this port went through.

## Step by step

1. **Read the source dashboard's own four files start to finish before writing anything** — its `.yml`, `.json.py`, `.js`/`.css`, `.md`. Note every convention that isn't obvious from the YAML alone: a `HIDDEN_WIDGET_NAMES` loader-level skip, a hand-written one-off SQL query merged onto a widget's result outside the YAML pipeline (e.g. this repo's own `inventory.json.py`'s `dv_project_names()`, or `bridge.json.py`'s `DV_SURVIVOR_SQL`), a `TITLE_OVERRIDES`/`WIDGET_TITLE_OVERRIDES`/`TAB_TITLE_OVERRIDES` display-only rename, a named-widget chart override (`DONUT_WIDGET_NAMES`, `AGE_HISTOGRAM_WIDGET_NAME`). These never show up in a plain YAML diff and are exactly what gets missed on a first pass.

2. **Copy the YAML into the destination's DAC repo verbatim first**, then adapt only what must differ: the BigQuery project/dataset/table names in every `sql:` block, and nothing else in the SQL logic itself unless the destination's own data genuinely requires it (e.g. a category the destination's Sheet doesn't have — confirm this live before assuming, don't guess). Keep the destination's own filter option labels only if the destination explicitly wants different ones; otherwise match the source's filter shape exactly, including which tabs a given filter does/doesn't apply to.

3. **Build the loader, renderer, and page following the source's own structure**, not a from-scratch design — same `widget_by_id`/`sql_templates` dedup-by-rendered-SQL approach, same `DISPLAY_KEYS` list, same `HIDDEN_WIDGET_NAMES`-with-`continue` convention, same named-widget-override pattern in the renderer for anything the source special-cases ahead of its normal dispatch. Where the destination's own data genuinely differs (a measure that doesn't exist on the source, a category the source doesn't have), add it the same way the source would — a one-off SQL template merged onto an existing widget's result by name, not a wholesale restructuring.

4. **Do the first side-by-side comparison against the source's own *rendered* output, not its YAML.** Open the source's live page (or a local preview) next to the destination's, tab by tab, and check: every widget that's visible on one is visible on the other (a widget can exist in the YAML but be hidden by `HIDDEN_WIDGET_NAMES` — a plain YAML diff will miss this entirely, which is exactly what happened on this port's "system engagement tabs don't pass my side-by-side test" round); every label, note, and filter-caveat reads the same wording; every chart type (donut vs. bars, stacked vs. grouped) matches for widgets that are supposed to match. Treat a maintainer's "this looks like an older version" or "clean up the extra widgets/legends" report as a cue to re-run this comparison yourself before touching code, not as a one-off bug to patch.

5. **For every gap found, decide: is this a genuine source-level fix, or a display-only override?** Two different fixes exist for the same symptom, and using the wrong one causes drift later:
   - **Source-level** (edit the destination's own DAC YAML, same as any other DAC change): the underlying thing is genuinely supposed to be identical in scope/logic between the two sites — wrong project-type scope, a stale filter-note sentence, missing widgets. Make the destination's YAML say what the source's does.
   - **Display-only** (override in the destination's own `.js`, YAML untouched): the two sites' YAML legitimately differ in wording/structure for reasons that have nothing to do with data (the destination's own dashboard was independently authored and used `**Bold labels:**` where the source uses `### headings`, or a widget's internal DAC name differs from its desired display title) — write a `TITLE_OVERRIDES`-style map or a renderer change, and say explicitly in CLAUDE.md why this one stayed display-only instead of touching the source of truth. Never silently pick one without recording the reasoning; a future reader needs to know which YAML edits are "real" fixes vs. which display code is covering for independently-authored source text.

6. **If the destination repo must never name or reference the source site/org** (confirm this with whoever asked — it was an explicit standing constraint on this port, not a universal rule), scrub every commit, CLAUDE.md edit, and code comment before committing: grep the full diff for the source org's name and any of its repo/service/bucket name fragments (this port's own list: `grep -iE "baltimore|baldash|balkpis|balspm|balbridge|balhmiscsv|baldashboard"`, generalize to the actual source's own identifiers) and make that grep a mandatory pre-commit step, every single commit, not just the first. Refer to the source dashboard only as "the sibling dashboard" / "a similarly-structured dashboard built for another CoC's site" in prose. This applies to CLAUDE.md prose and code comments just as much as to visible page text — a code comment is still a public file in a public repo.

7. **Verify without live BigQuery access, same discipline as `dashboard-dark-theme`'s step 7.** Build a synthetic fixture generator that mirrors the loader's *exact* widget/column shape — including which columns a table widget's `columns:` config declares vs. silently omits (a declared-but-`hidden: true` column and an undeclared one both disappear from the rendered table, but the fixture's row-shape must still match whichever the loader actually selects in SQL, or the fixture will desync from reality the moment a column list changes). Run `npx observable preview`, verify with Playwright using both a screenshot AND direct DOM text/attribute extraction (`inner_text()`, `getComputedStyle(...)`, a column-header list) — a screenshot alone confirms it looks right, not that the exact wording/column set matches; this port caught real mismatches (a stale footer link, an unhidden column) that read as "fine" in a screenshot. Check both themes if the dashboard has `dashboard-dark-theme` applied. Clean up the fixture and confirm no stray preview process before moving on.

8. **Commit and push in dependency order: the `-dac` repo first, then the public repo** (the public repo's own copy of the YAML, and any display logic reacting to it, depends on the DAC repo's content being final). Before opening a PR, re-run the no-mention grep from step 6 on the actual diff, not just the files you remember touching. If a branch's PR already merged and there's follow-up work, start a **fresh branch off the latest `origin/main`** (`git fetch origin main && git checkout -B <new-branch> origin/main`, then `git stash`/`stash pop` across the branch switch if there's uncommitted work) — never stack new commits on an already-merged branch's history.

9. **After merging, watch the deploy build to completion and confirm the *live* site, not just the build log.** Poll the workflow run via `gh api repos/<owner>/<repo>/actions/runs/<id>` (a `Monitor` poll loop, not a sleep-in-a-loop) until `status=completed`, then fetch the live page's actual data file and check the specific thing that changed. Observable Framework content-hashes its data file names and serves them at a different path than the page's own relative import suggests (`../data/<name>.json` in the page source resolves to `/<site>/_file/data/<name>.<hash>.json` when fetched directly, not the naive `/<site>/data/<name>.<hash>.json`) — grep the live page's HTML for the `FileAttachment` metadata block (`"path":"../_file/data/..."`) to get the real URL rather than guessing.

10. **Update CLAUDE.md in both repos in the same pass as the code change, not as a follow-up.** Match the existing voice exactly: "per explicit request", reasoning about *why* a choice was made (not just what changed), and — if step 6's constraint applies — the source referred to only as "the sibling dashboard". A reader of either repo's CLAUDE.md alone should be able to tell which parts are genuinely data-equivalent to the source and which are this destination's own deliberate departure.

## Gotchas that will burn you

**A YAML diff is not a parity check.** The single biggest source of missed gaps on this port was comparing the two dashboards' raw YAML side by side and calling it done — missing that a widget present in both YAMLs was hidden from one site's *live* page by its own loader's `HIDDEN_WIDGET_NAMES`. Always compare rendered output (step 4), YAML diffing is a starting point at best.

**"Matches the sibling's wording" can mean two different YAML structures.** This port's own About-panel text looked the same once rendered (an intro paragraph plus two side-by-side definition blocks) whether built from `**Bold label:**` splitting or `### Heading` splitting — but the destination's `renderAbout()` had to match the *source's* actual split regex once the YAML content was changed to use real markdown headings, or the headings would render as plain bold text with no semantic `<h3>`. When you change a YAML widget's content structure to match a source, always check whether the renderer code that parses it needs the matching change, not just the text.

**The same underlying thing can be hidden two different ways across different widgets in the same source dashboard.** This port's "Report quarter" column was dropped via `hidden: true` in one QoQ table's `columns:` list, but simply never declared at all in another QoQ table that also computes it in SQL. Don't standardize on one approach when porting — match each widget's own existing convention exactly; the SQL still needs to compute the column either way (for the `LAG()`/latest-period logic), only the display-side column list differs.

## Reference implementation

The Baltimore → Westchester Bridge to Housing port: `hmisguru/baltimore`'s `bridge/balbridge.yml` + `src/data/bridge.json.py` + `src/components/bridge.js`/`.css` + `src/bridge/index.md` (source) ported into `hmisguru/westchester`'s `bridge/dashboard.yml` + `src/data/dashboard.json.py` + `src/components/dashboard.js`/`.css` + `src/bridge/index.md`, DAC source in `hmisguru/westchester-dac`'s `dashboard.yml`. Went through an initial build, then successive parity rounds: full YAML feature-match (Age pie/table, 3 engagement-trend widgets), a scope correction (PSH removed from project-type filter to reflect "interim housing" only, confirmed via the destination's own explicit instruction, not assumed), a System Engagement tab widget/legend cleanup caught by a maintainer's own side-by-side test, filter-note and page-title wording matches, an About-panel text/structure match, and a final column-visibility + footer-link cleanup pass — each round driven by a fresh rendered-output comparison, not a diff of the two YAMLs.
